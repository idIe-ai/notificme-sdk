# Changelog

## Unreleased

### Added

- **Lists and quotes in the light Markdown** (card `text` block and a question's `context`; never the notification `summary`), line by line at column 0: `- item` (bullet), `1. item` or `1) item` (numbered, 1 to 3 digits, the number kept as written), `> text` (quote). Consecutive lines of the same kind form one list or quote; an empty line or a line of another kind ends it; no nesting; `\- `, `\>` and `\1. ` show the marker as text. `InlineMarkdown.blocks()` returns `MdBlock.Text`, `MdBlock.ListBlock` and `MdBlock.Quote`; `InlineMarkdown.plain()` now writes `• item`, `3. item` and the quote's text (push and previews). `parse()` is unchanged. The same rules run on the web and on the server.
- `cards`: `LightMarkdownText` draws those blocks (bullets in the accent color, numbers aligned with a hanging indent, quotes with a bar at the left); the `text` block uses it. `cards-wear`: `WearMarkdownText`, the compact version for the watch, used by `WearBlock`; `WearDecisionCard` shows the context with `InlineMarkdown.plain()`.
- `Notification.sourceIconUrl` now comes from the service that sent the event or question (the token's owner), so a service whose events carry another `source` text (`confirmo` from the service `confirmo.com.br`) still shows its icon, and no service can borrow another's icon through the `source` text. `InboxSnapshot.SCHEMA` = 3: caches resync once to get it.
- `Notification.sourceIconUrl`: the image of who sent it (`source_icon_url` from `GET /v0/sync`, a path to resolve with `NotificClient.urlOf`): the person's photo; from a service, its icon (set by the workspace owner) or else the logo of the organization it belongs to; null = show the initials. `Notification.sourceName` now also carries a person's name for messages from `@handle`, and `Notification.sourceKind` (`person` or `service`) with `Notification.fromPerson` tell a person from a service (a service's event with source `@someone` stays a service). `InboxSnapshot.SCHEMA` = 2, so caches resync once and get them.
- `Notification.sourceName`: the display name of the service that sent it (`ERP` for source `erp`), from `GET /v0/sync` (`source_name`); null when the source is not a named service.
- `InboxSnapshot.schema` (`InboxSnapshot.SCHEMA` = 1): a cache saved by an older SDK is shown at once, then synced again from cursor 0 once and replaced, so notifications cached before a new field (like `sourceName`) get it. Costs one full sync after the update.
- **Linking a watch** in `client`: `NotificClient.createDeviceLinkCode()` (a one-time code, 2 minutes, once) and `Auth.linkDevice()` (the watch exchanges it for a session of its own, registered as a device). Plan B, like a TV sign-in: `Auth.startDeviceLink()` (a code to show), `NotificClient.approveDeviceLink()` (approved on a signed-in device) and `Auth.pollDeviceLink()`. `client-android` registers a watch as platform `wearos` (`NotificAndroid.PLATFORM_WEAR_OS`), named as the person named it (`WatchLinkClient.localName()` reads the name a Galaxy Watch keeps only in Bluetooth), and its reactions say `wearos` too.
- **"Got it" (acknowledgment)** in `client`: `NotificClient.acknowledge()` and `Inbox.acknowledge()` (read plus an action reaction `acknowledged`, recorded as evidence and shown on every device as `Notification.acknowledgedAt`), and `Notification.asksForAck` (an open critical alert or a message from a person still waiting for it).
- **`client-wear`** (Wear OS Data Layer, `MessageClient` only, a few bytes per message): the watch asks to be linked and the phone answers with `LinkCode`s; the phone forwards what arrives (`RelayItem`, with what a reply needs, so the watch shows and answers it without the network); `Handled` both ways ("got it", answered, read, being read, snoozed) so the other side stops ringing; the phone opens a watch screen (`PhoneLink.openOnWatch`, through `RemoteActivityHelper`). Phone side: `PhoneLink`, `PhoneBridgeService`; watch side: `WatchLinkClient`, `PhoneEventsService`. Protocol constants in `WatchLink`. The link request names the accounts the watch already has (`WatchLinkClient.requestLink(linked)`, `PhoneBridgeService.linkCodes(nodeId, linked)`), so the phone sends codes only for the missing ones; an empty answer means nothing new.
- **`cards-wear`** (Compose for Wear OS): `WearInboxCard`, `WearNotificationCard` and `WearDecisionCard` for inbox rows; `WearBlock` and `Card.watchBlocks()` for card blocks on a small round screen (a chart becomes a sparkline, a table "column: value" lines); `wearQuestionItems` for the questions in a `TransformingLazyColumn`; `WearAnswerState` and `QuestionSet.watchSupport()` (what a watch can answer: `maxLevel`, `dictation`, `maxOptions`; `WatchBlocker` when it can't). Texts in English, Portuguese (Brazil) and Spanish.
- Answers spoken on the watch: with dictation, `text` and `voice` questions take the transcription as `free_text`, `number` the number said (`WearAnswerState.parseSpokenNumber`, in the watch's language) and a `single` with `allow_other` a spoken "Other…". The app runs the speech recognizer and hands the text back with `WearAnswerState.setSpoken`.

### Fixed

- **`Inbox` recovers from a sync reset.** When `GET /v0/sync` answers `reset: true` (the server no longer knows the saved cursor), the inbox clears the list, moves the cursor back to 0 and reads everything again in the same refresh. Before, it kept sending the old cursor and wiped the list on every refresh. The cursor is now a global position (server ADR 0012) that only ever comes from `next_cursor` or the gateway's `ready`; the `seq` of a live delivery or of a push is informational and is never used as a cursor.
- **`cards` tables fit the screen.** Columns of numbers (`150`, `1,090.00`, `US$ 3,842.60`, `-4%`) are right-aligned and never wrap; text columns wrap so the numbers fit. Only a table too wide even then scrolls sideways, and it fades at the edge that has more to show (a fourth column used to be cut off with no hint).

## 0.1.0

- First version of `client` and `client-android`: sign-in by e-mail, person tokens, inbox sync with realtime catch-up, question sets and signed replies, reactions, devices, groups, contacts and the electronic signature. `cards` renders the 10 card blocks and the 7 question types with Jetpack Compose.
